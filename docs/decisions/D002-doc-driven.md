# D002 — 文档驱动开发流程

## 上下文

Agent 辅助开发容易陷入"对话驱动"的模式——需求在对话中描述，实现没有落盘，决策无法追溯。需要一种稳定的工作方式。

## 参考

借鉴 clowder-ai 项目的文档体系：Feature Spec + ADR + Lessons Learned + Vision-driven。简化适配单人开发场景。

## 决策

采用 **Spec 驱动** 的文档工作流：

```
你写需求 → 我写 Spec → 你审阅 → 我实现 → 我测试 → 我反思
              ↑                              |
              └──── 落盘为文档 ←─────────────┘
```

### 文档结构

| 目录 | 用途 | 何时写 |
|------|------|--------|
| `docs/VISION.md` | 项目愿景，决策锚点 | 项目启动时，重大方向调整时 |
| `docs/ROADMAP.md` | 当前迭代路线图 | 每个 Phase 开始前 |
| `docs/specs/S{NNN}-*.md` | 功能规格 | 实现前 |
| `docs/decisions/D{NNN}-*.md` | 架构决策记录 | 做出技术决策时 |
| `docs/lessons/L{NNN}-*.md` | 经验教训 | 踩坑后 |
| `docs/devlog/{date}-*.md` | 开发日志 | 实现过程中 |

### 核心原则

1. **文档是沟通媒介**：需求通过文档传达，不依赖对话上下文
2. **决策留痕**：技术选型、架构取舍都进 decisions/
3. **Spec 可变更**：需求变了更新 spec，标记变更原因
4. **反思必落盘**：踩坑了必须写 lessons/

## 后果

- 前期文档工作量略大，但后期维护和回溯成本大幅降低
- Agent 可以在任意时刻通过阅读文档恢复上下文，不依赖对话历史
