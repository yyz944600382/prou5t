# D005 — 分支策略与质量保障

## 上下文

项目需要明确分支管理规则和代码质量保障机制。

## 决策

### 分支策略

- **禁止在 main 分支上直接开发**
- 每个 Spec 对应一个开发分支：`dev/s{NNN}-{slug}`
- 完成后提 PR → 审查通过 → 合并到 main
- 示例：`dev/s001-project-skeleton`

### 质量保障

采用 Claude 内部多角色方案：

```
Claude (实现者) — 在 dev 分支写代码 + 单元测试
       │
       ▼
Claude (审查者) — /code-review 审查代码质量、spec 符合度
       │
       ▼
用户 — 最终审批合并
```

三个角色，同一个模型，但职责分离、视角不同：
- **实现者**关注"把功能做出来"
- **审查者**关注"做得对不对、有没有遗漏"
- **用户**关注"是不是我想要的"

### 合并流程

1. 在 `dev/s{NNN}-xxx` 分支完成开发和测试
2. 跑 `/code-review` 做自动审查
3. 推送到 GitHub / Gitee
4. 用户审阅后合并到 main（或打回修改）

## 后果

- 每个 Spec 有独立的开发分支，代码历史清晰
- 审查者与实现者角色分离，减少盲区
- 合并前必须有审查记录
